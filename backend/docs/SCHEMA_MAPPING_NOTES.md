# Schema mapping notes

Per the build prompt (§0): "the artifact wins" — where this document (or the
build prompt) names a field that does not exist in the attached CBDT JSON
schema (`ITR-1_2026_Main_V1_1.json`), the schema's name is used and the
discrepancy is logged here.

This file reconstructs the original `itr1-module` project's
`docs/SCHEMA_MAPPING_NOTES.md`, deleted along with that project before it was
committed to git. Its content is regenerated by directly comparing the real
schema (as loaded by `itr1/serialize/schema_order.py`) against the build
prompt's §11.2 "expected skeleton", which the prompt itself calls "a
navigational aid, not a specification."

---

## Root structure: schedules are top-level siblings of `ITR1`, not nested under `ITR1_IncomeDeductions`

The build prompt's §11.2 skeleton suggests:

```
ITR1_IncomeDeductions (Salary block, HP block, other sources, GrossTotIncome,
                        DeductUndChapVIA, TotalIncome, exempt income schedules,
                        Schedule80D / 80G / 80GGA / 80GGC / 80DD / 80U / 80C /
                        80E / 80EE / 80EEA / 80EEB / 10(13A) / 24(b))
```

…implying the Chapter VI-A schedules nest inside `ITR1_IncomeDeductions`. The
real schema places them as **top-level siblings of `ITR1_IncomeDeductions`**,
directly under `ITR1` itself:

```
ITR1
├── CreationInfo
├── Form_ITR1
├── PersonalInfo
├── FilingStatus
├── ITR1_IncomeDeductions   (only Salary/HP/OtherSources/GTI/DeductUndChapVIA totals — NOT the schedules)
├── ITR1_TaxComputation
├── TaxPaid
├── Refund
├── Schedule80G             ← top-level, not nested
├── Schedule80GGA           ← top-level
├── Schedule80GGC           ← top-level
├── Schedule80D             ← top-level
├── Schedule80DD            ← top-level
├── Schedule80U             ← top-level
├── Schedule80E             ← top-level
├── Schedule80EE            ← top-level
├── Schedule80EEA           ← top-level
├── Schedule80EEB           ← top-level
├── Schedule80C             ← top-level
├── ScheduleEA10_13A        ← top-level (HRA schedule; note the name — not "Schedule10_13A")
├── TDSonSalaries           ← top-level ("Schedule TDS1" in the prompt's prose)
├── TDSonOthThanSals        ← top-level ("Schedule TDS2")
├── ScheduleTDS3Dtls        ← top-level ("Schedule TDS3")
├── ScheduleTCS             ← top-level ("Schedule TCS")
├── TaxPayments             ← top-level ("Schedule IT" — advance tax / self-assessment tax challans)
├── LTCG112A                ← top-level
├── Verification
└── TaxReturnPreparer
```

**Resolution:** `itr1/serialize/serializer.py` builds the payload against
these real top-level names; `itr1/serialize/schema_order.py` walks the actual
schema (resolving every `$ref`) to derive property order and to prune empty
nodes, so the ordering is schema-derived rather than hand-maintained. Verified
directly: a generated payload for the golden case has top-level `ITR1` keys
`CreationInfo, Form_ITR1, PersonalInfo, FilingStatus, ITR1_IncomeDeductions,
ITR1_TaxComputation, TaxPaid, Refund, TDSonSalaries, Verification` (the
schedule nodes that are empty for that case are correctly omitted per the
"omit empty nodes" non-negotiable in §11.1).

## `FilingStatus` seventh-proviso field names

The schema's actual field names for the seventh-proviso sub-conditions are
considerably more specific than the build prompt's prose ("capture the
sub-conditions"): `IncrExpAggAmt2LkTrvFrgnCntryFlg`, `AmtSeventhProvisio139ii`,
`IncrExpAggAmt1LkElctrctyPrYrFlg`, and further amount/flag pairs. The
`ReturnModel` (see `itr1/model_blank.py`'s `filingStatus.seventhProviso`)
normalises these into domain-level names
(`travelExpenseAbove2Lakh`/`travelExpenseAmount`/`electricityAbove1Lakh`/
`electricityAmount`/`clauseIvApplies`) per architecture mandate 3 ("the JSON
serializer is the only component that knows CBDT element names") —
`itr1/serialize/serializer.py` is where the real schema names are used; the
model and every screen upstream of it never see them.

## `ReturnFileSec` enum: code 16 is 153C, not 139(8A) — and 139(8A) has no code at all

The schema's own `description` string on `FilingStatus.ReturnFileSec` spells
out every enum value exactly: `11: 139(1)-On or before due date, 12:
139(4)-After due date, 13: 142(1), 14: 148, 16: 153C, 17: 139(5)-Revised, 18:
139(9), 20: 119(2)(b)-After condonation of delay`.

**This caught a real mislabeling bug**, not just a documentation gap: an
earlier pass of `itr1/forms.py`'s `RETURN_FILE_SEC_CHOICES` had code `16`
labeled `"139(8A) — updated"`, inferred from the build prompt's §4.4 radio-group
prose (`139(1) · 139(4) · 139(5) · 119(2)(b) · 139(8A)`) without checking the
schema's own description string. The schema says code 16 is **153C**, not
139(8A). Fixed directly in `forms.py` once found — verified no engine logic
(`itr1/engine/`) ever branched on `returnFileSec == 16` assuming the wrong
meaning, so this was a UI-label-only bug, not a computation defect.

Separately: the build prompt's §4.4 first radio group calls for a `139(8A)
updated` option, but **the schema's `ReturnFileSec` enum has no code for
139(8A) at all** (searched the full schema text for "139(8A)" and "Updat*" —
zero matches). This is a genuine schema limitation: there is no way to record
a 139(8A)-updated-return filing in a schema-valid ITR-1 payload for this
schema version, so it is not offered as a filing-section option.

## `Digest` field has no CBDT-published computation method

`CreationInfo.Digest` is declared as a string in the schema with no
`pattern`/`format` constraint and no publicly documented computation algorithm
in the attached validation-rules PDF. `constants.json`'s `creationInfo.digest`
currently supplies a static placeholder (`"-"`), which is schema-valid (any
string satisfies the declared type) but is **not** a real integrity digest of
the payload. If a genuine CBDT-specified digest algorithm surfaces (e.g. in a
future schema-change document), it belongs in
`itr1/serialize/serializer.py`'s `CreationInfo` block, replacing the constant.
